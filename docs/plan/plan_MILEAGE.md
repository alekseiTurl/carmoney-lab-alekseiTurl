# План MILEAGE: пробег не больше 400 000 км, иначе решение review

Дата: 2026-09-24. План сверен с фактическим кодом (не только с
`docs/setup/code_map.md` — карта местами устарела, см. «Риски», п. 5).

## Правило

После расчёта решения по LTV: если пробег больше 400 000 км, решение по
заявке становится `review`. Граница «не больше 400 000» — включительная:
`mileage <= 400000` правило не срабатывает, `400001+` — срабатывает.
Порог выносим в `backend/config/rules.php` (новый ключ
`vehicle.review_mileage_km`), в коде не хардкодим.

**Допущение по умолчанию** (закреплено тестами, пока заказчик не ответил
на вопрос 1): правило понижает только `approve` до `review`. Решения
`reject` и `review` не меняются — высокий пробег не ослабляет отказ по LTV.

## 3. Тесты

Граничные значения — отдельными строками. Все тесты — по стилю AAA,
имя описывает поведение. payload везде валиден по остальным полям
(VIN, год, стоимость, сумма, срок).

В `tests/Unit/AssessmentServiceTest.php`:

1. Пробег `399999`, LTV 50.0 → `approve`, `approved_limit` = запрошенной
   сумме (порог не сработал, решение не изменилось).
2. Пробег `400000`, LTV 50.0 → `approve`, `approved_limit` = запрошенной
   сумме (граница «не больше» включительная — правило не срабатывает).
3. Пробег `400001`, LTV 50.0 → `review`, `approved_limit` = 0 (правило
   сработало на первое значение за границей).
4. Пробег `500000`, LTV 50.0 → `review` (верхняя граница зоны
   пересечения с `max_mileage_km`: валидацию проходит, решение — review).
5. Пробег `400001`, LTV 95.0 → `reject` (закрепляет допущение: высокий
   пробег не ослабляет reject; тест меняется, если заказчик ответит
   иначе на вопрос 1).
6. Пробег `400001`, LTV 75.0 → `review` (review по LTV остаётся review,
   `approved_limit` = 0).

В `tests/Unit/ApplicationValidatorTest.php` (фиксация текущего
поведения валидатора, до нового правила эти заявки не доходят):

7. Поле `mileage` отсутствует → `ValidationException`, в `errors()` ключ
   `mileage` (сейчас `?? -1` превращает отсутствие в −1 → ошибка
   «Пробег от 0 до 500000 км»).
8. `mileage = null` → `ValidationException`, ключ `mileage` (то же
   поведение, что отсутствие поля).
9. `mileage = ''` → валидацию проходит, нормализуется в `0` км
   (существующий нюанс: `(int) ''` = 0). Тест фиксирует это как есть;
   желаемое поведение — вопрос 2.

## 4. Риски

1. **Пересечение с `max_mileage_km` (500000)** — главная зона внимания.
   Жёсткий предел в `ApplicationValidator` (строки 43–46) отсекает
   пробег > 500 000 ошибкой 422 — до решения такие заявки не доходят.
   Новое правило работает только в зоне 400 001..500 000. Риски:
   (а) по ошибке внести новое правило в `ApplicationValidator` — тогда
   400 001+ станет ошибкой 422 вместо review; (б) ожидание, что
   «review» получит и заявка с пробегом 600 000 — нет, она получит 422.
   Оба риска закрыты тестами 3, 4 и 7.
2. **Смена сигнатуры конструктора `AssessmentService`** ломает все точки
   сборки. Таких точек ровно две: `AppFactory.php:30` и
   `AssessmentServiceTest.php:24` (Feature-тестов и других мест сборки
   нет — проверено поиском). Пропущенная точка даст fatal на запуске
   или в тестах, поэтому шаги 2–4 делаются одним коммитом.
3. **approved_limit при понижении.** Если правило вставить после
   формирования массива результата (строки 35–41), при approve → review
   в ответе останется ненулевой лимит. Контроль: тест 3 проверяет
   `approved_limit === 0`.
4. **Граница «не больше»**: смена условия на `>=` (400 000 → review)
   молча ломает допущение. Контроль: тесты 2 и 3 ломаются первыми.
5. **`docs/setup/code_map.md` устарел по цифрам**: там `approve_max` 60.0
   (строка 35), фактически в `rules.php:44` — 65.0. Место вставки
   правила из карты (`AssessmentService.php:33`) актуально. Обновление
   code_map в задачу не входит — план опирается на фактический код.
6. **Приведение типов**: дробный пробег в пейлоаде (`"400000.7"`)
   обрезается до `400000` ещё в валидаторе (`(int)` на строке 43) —
   правило сравнивает уже целое. Не ломает, поведение существующее.
7. **БД и хранение**: `db/schema.sql` ENUM `decision` уже содержит
   `review`, миграций и правок schema/seed не нужно; исторические
   заявки и seed-данные не пересчитываются.

### Что не входит

- `frontend/` — тексты, подсказки и валидация формы не меняются.
- Значение и текст ошибки `max_mileage_km` (500 000) — без изменений.
- LOAN-12 — расчёт лимита по `rules.ltv_by_age`.
- Расхождение `<` / `<=` на границе `approve_max` в `DecisionEngine`
  (существующее поведение) — не чиним в этой задаче.
- Причина review (поле `reason`) в ответе API — не добавляем.
- Обновление `docs/setup/code_map.md`.
