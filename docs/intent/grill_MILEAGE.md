# Grill-интервью MILEAGE: пробег не больше 400 000 км, иначе review

Дата: 2026-09-24. Режим Grill Me: вопросы по одному, не больше шести,
только влияющие на реализацию. Задано 4 из 6.

Перед интервью сверены `docs/setup/code_map.md` и `docs/plan/plan_MILEAGE.md`
(оба есть, план датирован 2026-09-24 и сверен с фактическим кодом).

## Что не спрашивалось — уже зафиксировано в плане

- Граница 400 000 включительная: `<= 400 000` не срабатывает, `400 001+` —
  срабатывает; порог в `backend/config/rules.php` (`vehicle.review_mileage_km`),
  в коде не хардкодим.
- Пробег отсутствует / `null` → 422 валидации с ключом `mileage`, до расчёта
  решения заявка не доходит (тесты 7–8 плана фиксируют).
- Вне scope: фронтенд, значение/текст ошибки `max_mileage_km` (500 000),
  LOAN-12, расхождение `<`/`<=` на `approve_max`, пересчёт исторических
  заявок и seed, обновление code_map.

## Вопрос 1 — reject и высокий пробег

Вопрос: план по умолчанию — правило понижает только approve до review;
если LTV уже дал reject, высокий пробег его не ослабляет (тест 5 плана:
пробег 400 001, LTV 95 → reject). Подтверждаете допущение?

Варианты: (1) только approve → review; (2) reject тоже → review;
(3) правило не понижает, а блокирует approve (по эффекту = 1).

Ответ: **«Только approve → review»** (рекомендованный, подтверждён).

Решение: reject по LTV остаётся reject при любом пробеге, review по LTV
остаётся review. Шаг 2 плана и тест 5 — без изменений.

## Вопрос 2 — пустая строка в mileage

Вопрос: `mileage = ''` сейчас нормализуется валидатором в 0 км, заявка
проходит до решения и может получить approve (план фиксирует это тестом 9,
код валидатора не меняет). Ожидаемое поведение — оставить как есть или
сделать 422-ошибку?

Ответ: **«Оставить как есть: 0 км»** (рекомендованный, подтверждён).

Решение: `ApplicationValidator` не трогаем, scope не расширяется; тест 9
фиксирует текущее поведение.

## Вопрос 3 — причина review в ответе API

Вопрос: нужна ли причина review в ответе API (например,
`reason: high_mileage`), чтобы фронтенд и аналитика видели, почему решение
изменилось? План по умолчанию — не добавляем.

Ответ: **«Добавить reason»** — отступление от плана (в разделе «Что не
входит» поле reason было исключено).

Решение: поле reason добавляется в ответ API — правка формирования ответа
в `AssessmentService::assess()` и тесты. `docs/plan/plan_MILEAGE.md`
нуждается в правке при реализации.

## Вопрос 4 — когда reason появляется и с какими значениями

Вопрос: правило понижает только approve → review, но review бывает и просто
по LTV (60–85). Когда в ответе появляется reason и что содержит?

Варианты: (1) только `high_mileage` при понижении по пробегу;
(2) reason для всех review (`high_mileage` / `high_ltv`);
(3) reason всегда (approve/review/reject).

Ответ: **«Только high_mileage»** (рекомендованный, подтверждён).

Решение: `reason: "high_mileage"` появляется только когда правило пробега
понизило approve → review. При review по LTV, approve и reject поле
отсутствует.

## Сводка решений для intent

1. Правило: после решения по LTV, если `approve` и `mileage > 400 000` →
   `review`; граница включительная, порог в `rules.php`.
2. Понижает только approve → review; reject и review по LTV не меняются.
3. Пробег отсутствует / `null` → 422; `''` → 0 км как есть, валидатор
   не трогаем.
4. `reason: "high_mileage"` — только при срабатывании правила пробега;
   в остальных решениях поля нет.
5. Вне scope — как в плане (см. выше), кроме reason: теперь входит.
