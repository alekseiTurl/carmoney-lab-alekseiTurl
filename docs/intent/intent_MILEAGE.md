# Замысел MILEAGE: проверка пробега в расчёте решения по заявке

Дата: 2026-09-24. Задача: MILEAGE.
Лог интервью: `docs/intent/grill_MILEAGE.md` (вопросы 1–4).
Исходная формулировка (ответ в интервью): «добавить в расчёт решения по
заявке проверку — пробег авто не больше 400 000 км, иначе решение review».

## 1. Замысел

В расчёт решения по заявке добавляется проверка пробега: если пробег авто
больше 400 000 км (граница «не больше» включительная), решение понижается
с approve до review; reject и review, полученные по LTV, понижение не
затрагивает. В ответе API у заявки, пониженной по пробегу, появляется
причина — `reason: "high_mileage"`.

## 2. Зачем

Авто с пробегом выше порога не должно получать автоматический approve —
решение таких заявок уходит на ручную проверку (review). Поле `reason`
даёт фронтенду и аналитике видимость, почему решение изменилось.

## 3. Constraints

1. Порог 400 000 км, граница включительная: пробег ≤ 400 000 — правило
   не срабатывает, 400 001 и больше — срабатывает.
   Источник: ответ в интервью — исходная формулировка «не больше
   400 000 км».
2. Превышение порога — решение review, а не ошибка валидации: заявка с
   высоким пробегом остаётся валидной и доходит до расчёта решения.
   Источник: ответ в интервью — исходная формулировка «иначе решение
   review».
3. Правило понижает только approve → review. Reject по LTV остаётся
   reject, review по LTV остаётся review.
   Источник: ответ в интервью, вопрос 1.
4. `reason: "high_mileage"` появляется в ответе API только у заявки,
   пониженной по пробегу; при approve, reject и review по LTV поле
   отсутствует. Источник: ответ в интервью, вопросы 3–4.
5. У пониженной заявки `approved_limit` = 0: лимит выдаётся только при
   approve. Источник: код: `backend/src/Domain/AssessmentService.php`
   (запрошенная сумма при approve, иначе 0) + ответ в интервью, вопрос 1
   (решение становится review).
6. Правило действует только на заявки, прошедшие валидацию пробега
   (0..500 000 км). Пробег не указан или null → ошибка валидации,
   заявка до решения не доходит. Источник: код:
   `backend/src/Domain/ApplicationValidator.php`; предел 500 000 км —
   код: `backend/config/rules.php`.
7. Пустая строка в поле пробега трактуется как 0 км — текущее поведение
   сохраняем, валидацию не меняем. Источник: ответ в интервью, вопрос 2;
   текущее поведение — код: `backend/src/Domain/ApplicationValidator.php`.

## 4. Open questions

1. Буквальное прочтение формулировки «иначе решение review» допускало
   понижение и reject. Понижает ли правило только approve?
   **Закрыт**: ответ в интервью, вопрос 1 — только approve → review,
   reject и review по LTV не меняются.
2. Пустая строка в пробеге — 422-ошибка или 0 км?
   **Закрыт**: ответ в интервью, вопрос 2 — как есть, 0 км.
3. Нужна ли причина review в ответе API и когда она появляется?
   **Закрыт**: ответ в интервью, вопросы 3–4 — `reason:
   "high_mileage"`, только при понижении по пробегу.
4. Пересчитывать ли по новому правилу исторические заявки и seed-данные?
   **Открыт**: в интервью не отвечен (в плане было допущение «нет»,
   заказчиком не подтверждено).

## 5. Не входит

- Фронтенд: форма заявки, тексты и валидация на клиенте не меняются —
  задача про расчёт решения.
- Существующая жёсткая валидация пробега: предел 500 000 км и текст её
  ошибки — без изменений (код: `backend/src/Domain/ApplicationValidator.php`,
  `backend/config/rules.php`).
- Существующие пороги решения по LTV (approve/review/reject) — без
  изменений (код: `backend/src/Domain/DecisionEngine.php`).
- `reason` для решений, не пониженных по пробегу (review по LTV,
  approve, reject), — не добавляем (ответ в интервью, вопрос 4).
